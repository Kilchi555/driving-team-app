# Part A — Guthaben / Auszahlung / Affiliate / Gutscheine

## Finding 1 — Critical: Frozen withdrawal still spendable

### Files
- `server/api/customer/request-credit-withdrawal.post.ts` — freeze only via `pending_withdrawal_rappen`; `balance_rappen` unchanged
- `server/api/payments/process.post.ts` — uses `balance_rappen` without subtracting pending
- `server/api/courses/enroll-wallee.post.ts` — same pattern
- `server/api/admin/complete-withdrawal.post.ts` — pays out pending; balance clamped with `Math.max(0, …)`

Contrast (correct on some paths): `student-credits/use-for-appointment.post.ts`, `staff/process-bulk-payment.post.ts` respect freeze.

### Attack story
1. Student has CHF 100 credit.
2. Requests full withdrawal → `pending_withdrawal_rappen = 10000`, **`balance_rappen` stays 10000**.
3. Pays a lesson/course via `/api/payments/process` or `enroll-wallee` fully with credit — path sees 10000 available and spends it.
4. Admin completes withdrawal / exports IBAN transfer based on pending and wires CHF 100.
5. Student gets service **and** cash; school loses the amount.

## Finding 2 — High: Concurrent withdrawal requests inflate pending

### Files
- `server/api/customer/request-credit-withdrawal.post.ts` — read+check then update without conditional/`WHERE pending + amount <= balance`

### Attack story
1. Student with CHF 100 sends two parallel CHF 100 withdrawal requests.
2. Both read available = 100 and pass.
3. Both add to pending → `pending_withdrawal_rappen = 200` with `balance_rappen = 100`.
4. Admin complete/export treats 200 as payable → over-balance transfer.

---

## Finding 3 — High: Affiliate bank payout race

### Files
- `server/api/affiliate/request-payout.post.ts` — balance check then deduct without compare-and-swap

### Attack story
1. Affiliate with CHF 50 starts two parallel `type: 'bank'` payouts of CHF 50.
2. Both pass the balance check; both insert payout requests.
3. After SMS confirm, admin pays both → double payout.

---

## Finding 4 — High: Voucher redeem TOCTOU double credit

### Files
- `server/api/vouchers/redeem.post.ts` — credit applied before mark-redeemed; promo increment not atomic

### Attack story
1. Attacker has a valid shop gift card or promo credit code.
2. Sends two parallel POSTs to `/api/vouchers/redeem`.
3. Both see unredeemed / under max; both credit the wallet.
4. Code marked redeemed after — double credit already booked (spendable / withdrawable).

# Part B — Zahlung (Checkout / Pricing)

Audited paths: website/anonymous-sale/shop checkout, courses enroll-*, wallee/stripe create, booking create-appointment, appointment payment/discount endpoints, prices/discounts validate, invoices mark-paid, debug payment/webhook-test, client payment/wallee helpers.

## Finding 5 — High: Gift cards (`vouchers`) used as checkout discounts are never consumed

### Attack story
1. Obtain a shop gift card (`vouchers`, `redeemed_at IS NULL`), e.g. CHF 150.
2. Book via `POST /api/booking/create-appointment` with `discount_code` = gift code (any positive `discount_amount_rappen` enters the branch). Server applies `giftCard.amount_rappen` to the pending payment and **does not** set `redeemed_at`.
3. Reuse the same code on further appointments, or reduce other pending payments via `POST /api/appointments/apply-discount` (also no redeem).
4. Optionally still call `POST /api/vouchers/redeem` for full wallet credit (only redeem path sets `redeemed_at`).

**Money impact:** Unlimited underpayment equal to face value per use, plus optional double-spend via credit redeem.

### Evidence
- `server/api/booking/create-appointment.post.ts` — vouchers branch; no `redeemed_at` update
- `server/api/appointments/apply-discount.post.ts` — same
- Contrast: `server/api/vouchers/redeem.post.ts` marks redeemed

**Course note:** `enroll-wallee` / `process-public` also apply gift cards without redeeming. Full wipe to `serverAmount <= 0` is rejected by process-public; **partial** gift discounts remain reusable.

---

## Finding 6 — High: Course/shop checkout ignores discount usage limits

### Attack story
1. Tenant issues limited promo (`voucher_codes.max_redemptions=1` or `discounts.usage_limit=1`).
2. Enroll via `POST /api/courses/enroll-wallee` with that code.
3. Server recomputes discount from DB price but **never checks** redemption/usage limits.
4. `process-public` mirrors that — reduced Wallee charge proceeds.
5. Webhook may increment counters after pay; next enrollment still applies the code because charge paths never enforce the limit.

**Related:** `shop/create-payment.post.ts` recomputes discount from DB IDs in `metadata.discounts` but also does not check/increment limits — unlimited product-checkout reuse once an ID is known.

### Evidence
- `server/api/courses/enroll-wallee.post.ts` — no limit checks/increments
- `server/api/payments/process-public.post.ts` — same
- Contrast: `booking/create-appointment.post.ts` checks/increments for `voucher_codes` / `discounts` (gift cards still Finding 5)

## Suggested fixes (report only — not applied)

1. On withdrawal request: reduce spendable balance atomically (or make all spend paths subtract `pending_withdrawal_rappen`).
2. Atomic conditional updates for withdrawal pending, affiliate deduct, and voucher redeem (mark-redeemed / increment **before** or with credit under row lock / CAS).
3. When applying a `vouchers` gift card to any payment, atomically set `redeemed_at` (or remaining balance) with the discount write.
4. Enforce and atomically increment `max_redemptions` / `usage_limit` in `enroll-wallee`, `process-public`, and `shop/create-payment` before creating the charge.
