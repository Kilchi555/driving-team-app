# Geld-Sicherheitsbericht — Zahlung (Checkout/Pricing)

**Datum:** 2026-08-20  
**Scope:** Confirmed medium/high/critical only, Zahlung checkout/pricing paths listed in audit brief.  
**Method:** Code review of server charge/credit paths; client helpers only if server trusts them for money.

## Summary

Two **high** findings on discount/gift-card enforcement. No confirmed client-amount undercharge on the main Wallee/Stripe charge creators reviewed (those recompute from DB). Debug payment endpoints require `super_admin`. Client `utils/paymentService.ts` / `utils/walleeService.ts` are not trusted by server charge paths for amounts.

---

## Finding 1 — HIGH: Purchased gift cards (`vouchers`) applied as checkout discounts are never consumed

### Attack story

1. Attacker obtains a shop gift card (`vouchers` row) with e.g. CHF 150 (`amount_rappen`), still `redeemed_at IS NULL`.
2. Authenticated booking: `POST /api/booking/create-appointment` with `discount_code` = gift card code (and any positive `discount_amount_rappen` to enter the validation branch). Server loads the gift card, sets `validatedDiscountAmount = giftCard.amount_rappen`, writes a pending payment with reduced `total_amount_rappen`, and **does not** set `redeemed_at`.
3. Same code can be reused on further appointments via create-appointment or `POST /api/appointments/apply-discount` (also applies gift card balance to pending payments without marking redeemed).
4. Optionally, after repeated discount use, attacker still calls `POST /api/vouchers/redeem` and receives the **full** gift amount as wallet credit (redeem path is the only place that sets `redeemed_at`).

**Money impact:** Unlimited underpayment of lessons (and pending payment reductions) equal to the gift face value per use, plus optional double-spend via credit redeem.

### Evidence

- `server/api/booking/create-appointment.post.ts` — vouchers branch accepts unredeemed gift cards and never updates `redeemed_at` (usage tracking only touches `discounts` / `voucher_codes`).
- `server/api/appointments/apply-discount.post.ts` — gift-card branch reduces `payments.total_amount_rappen` without redeeming.
- Contrast: `server/api/vouchers/redeem.post.ts` correctly sets `redeemed_at` / `is_active: false` for the same table.

### Course path note

`enroll-wallee` / `process-public` also apply gift cards without redeeming. Full face-value wipe to `serverAmount <= 0` is rejected by `process-public`, so 100% free course via gift card alone fails; **partial** gift discounts remain reusable with the same non-consumption bug.

## Finding 2 — HIGH: Course checkout ignores `voucher_codes` / `discounts` usage limits

### Attack story

1. Tenant issues a limited promo, e.g. `voucher_codes` with `type=discount`, `max_redemptions=1`, or `discounts` with `usage_limit=1`.
2. Attacker enrolls via `POST /api/courses/enroll-wallee` with that `discountCode`.
3. Server recalculates discount from DB price but **never reads** `max_redemptions` / `current_redemptions` / `usage_limit` / `usage_count` before applying.
4. `process-public` recomputes the same way — still no limit check — and charges the reduced Wallee amount.
5. Webhook may increment counters after payment, but the next enrollment still applies the code because the enrollment/charge path never enforces the limit.

**Money impact:** A single-use (or N-use) course discount can be reused indefinitely for underpriced enrollments.

### Evidence

- `server/api/courses/enroll-wallee.post.ts` — discount validation: percentage/fixed only; no redemption/limit checks; no increment.
- `server/api/payments/process-public.post.ts` — server-side recompute mirrors that logic; no limit checks.
- Contrast: `server/api/booking/create-appointment.post.ts` does check and increment limits for `voucher_codes` / `discounts` (gift cards still broken — Finding 1).

### Related (same class) — shop

`server/api/shop/create-payment.post.ts` recomputes discount amounts from DB IDs in `metadata.discounts` but also **does not** check or increment `usage_limit` / `max_redemptions`. Same unlimited reuse for product checkout once a discount/voucher UUID is known (e.g. from validate response).

## Suggested fixes (report only — not applied)

1. When a `vouchers` gift card is applied to any payment, atomically set `redeemed_at` (or reduce remaining balance) in the same transaction as the payment/discount write; reject if already redeemed.
2. In `enroll-wallee`, `process-public`, and `shop/create-payment`, enforce and atomically increment `max_redemptions` / `usage_limit` before creating the charge.
