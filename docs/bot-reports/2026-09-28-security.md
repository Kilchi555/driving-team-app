## New findings

### 1. [High] Any authenticated tenant user can read arbitrary same-tenant payments via get-details

- **Location:** `server/api/payments/get-details.get.ts`
- **Attacker:** Authenticated low-privilege client in the same tenant
- **Controlled input:** `payment_id`
- **Attack path:** Authenticate as client → `GET /api/payments/get-details?payment_id=<victim>`. Auth + `tenant_id` filter only; no ownership/role check; returns full payment row plus payer name/email and items.
- **Impact:** Same-tenant disclosure of payment amounts, statuses, provider IDs, metadata, and customer PII.
- **Evidence:** `getAuthenticatedUser` then `.eq('tenant_id', …)` only; sibling `status.post.ts` enforces `payment.user_id === caller`.

### 2. [High] Voucher redeem accepts untrusted user_id/target_user_id without ownership or staff gate

- **Location:** `server/api/vouchers/redeem.post.ts`
- **Attacker:** Unauthenticated user (`user_id`) or any authenticated client (`target_user_id`)
- **Controlled input:** `code`, `user_id`, `target_user_id`
- **Attack path:** `POST /api/vouchers/redeem` with a valid code. Guest `user_id` picks credit recipient without auth; authed `target_user_id` is treated as staff-on-behalf with no role/tenant check. Credits `student_credits` and burns the code.
- **Impact:** Theft/misdirection of gift/promo credit; burning limited-use codes onto attacker-chosen accounts.
- **Evidence:** No staff role check on `target_user_id`; guest path accepts unauthenticated `user_id`.

### 3. [High] Unauthenticated reminder seed-templates overwrites global default templates

- **Location:** `server/api/reminder/seed-templates.post.ts`
- **Attacker:** Unauthenticated internet user
- **Controlled input:** None (POST trigger)
- **Attack path:** `POST /api/reminder/seed-templates` with no auth → service-role upsert of `reminder_templates` with `tenant_id=null`.
- **Impact:** Platform-wide sabotage of default email/SMS/push reminder copy.
- **Evidence:** No auth/CRON secret; immediate upsert loop.

### 4. [High] Public website API returns full tenants row including secret-bearing columns

- **Location:** `server/api/public/website/[subdomain].get.ts`
- **Attacker:** Unauthenticated user who knows a subdomain
- **Controlled input:** subdomain; optional `preview=1`
- **Attack path:** `GET /api/public/website/{subdomain}` (`?preview=1` also reads unpublished sites) → `tenants.select('*')` returned in JSON.
- **Impact:** Leakage of tenant integration/billing fields present on `tenants` (SARI credential columns, Stripe/Wallee identifiers, internal config) plus unpublished site content.
- **Evidence:** No auth; `select('*')`; `preview=1` bypasses `is_published`; migrations add SARI secret columns on `tenants`.

### 5. [High] Authenticated reminders manage get-logs is a cross-tenant reminder PII IDOR

- **Location:** `server/api/reminders/manage.post.ts`
- **Attacker:** Any authenticated user who knows an `appointmentId` or `userId`
- **Controlled input:** `action=get-logs`, `appointmentId` / `userId`
- **Attack path:** Authenticate → `POST /api/reminders/manage` with `get-logs` and victim id. No role/tenant/ownership check; `reminder_logs.select('*')` by caller-supplied id only.
- **Impact:** Cross-tenant disclosure of reminder recipients, subjects, and bodies (`mark-sent` similarly mutates by id alone).
- **Evidence:** `getAuthenticatedUser` only; get-logs has no tenant filter.

### 6. [High] Any authenticated client can list all same-tenant invoices

- **Attacker:** Authenticated low-privilege client in the same tenant
