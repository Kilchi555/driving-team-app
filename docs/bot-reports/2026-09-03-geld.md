## Offen — Critical

### C1 — Wallee-Transaktion umbinden + Sync ohne Betrags-/Uniqueness-Check

**Angriff:** Angreifer besitzt (1) eine teure offene Zahlung A ohne `wallee_transaction_id` und (2) eine günstige, bereits erfüllte Wallee-Tx (eigene kleine Zahlung B). Über `POST /api/payments/update-wallee-id` setzt der Owner die Tx-ID von B auf A (erlaubt, solange A noch keine andere ID hat). Anschliessend markiert `POST /api/payments/status` (Sync via `syncAndResolvePayment`) oder `POST /api/payments/process` (Existing-Tx-Pfad) A als `completed`/`authorized` allein aufgrund des Wallee-States — **ohne** Abgleich Captured Amount ↔ `total_amount_rappen`, **ohne** Unique-Constraint auf `wallee_transaction_id`.

**Belege:** `server/api/payments/update-wallee-id.post.ts` (Client-Attach wenn leer); `server/utils/wallee-payment-sync.ts` (`applyWalleeSyncDecision` / `mark_completed`); `server/api/payments/process.post.ts` (Completed-States → DB completed). Webhook-Pfad prüft Beträge — dieser Sync/Rebind-Pfad nicht.

### C2 — Eingefrorenes Auszahlungs-Guthaben via `/api/payments/process` ausgebbar

**Angriff:** Kunde stellt Auszahlung (`request-credit-withdrawal` → `pending_withdrawal_rappen`). Danach startet er die Begleichung einer eigenen Pending-Zahlung über `/api/payments/process`. Der Endpoint liest nur `balance_rappen` (nicht verfügbares Guthaben) und schreibt den Abzug non-atomar. Ergebnis: Termine/Leistungen mit eingefrorenem Guthaben bezahlt; Admin überweist trotzdem die Pending-Auszahlung.

**Belege:** `server/api/payments/process.post.ts` (Credit-Select/Deduct); Kontrast: `enroll-wallee` nutzt `availableWalletRappen` + `deductStudentCredit`.

### C3 — Affiliate-Auszahlung ignoriert `pending_withdrawal_rappen`

**Angriff:** Partner hat laufenden Studenten-Auszahlungs-Freeze. `POST /api/affiliate/request-payout` (type `bank`) prüft nur `balance_rappen`, zieht den Betrag non-atomar ab und legt `pending_sms` an. Eingefrorenes Guthaben wird so doppelt beansprucht (Bank-Payout + später complete-withdrawal).

**Belege:** `server/api/affiliate/request-payout.post.ts` (Balance-Check ohne Freeze; RMW-Update).

## Offen — High

### H1 — Parallele Auszahlungsanträge blähen `pending_withdrawal` auf

**Angriff:** Mehrere parallele `POST /api/customer/request-credit-withdrawal` lesen denselben Stand und addieren jeweils `amountRappen` auf `pending_withdrawal_rappen`. RPC `add_pending_withdrawal` existiert (`wallet-atomic.ts` / Migration), wird hier aber nicht genutzt. Pending kann Summe ≫ Balance erreichen.

**Belege:** `server/api/customer/request-credit-withdrawal.post.ts`.

### H2 — Affiliate Bank-Payout Race (doppelte Abbuchung)

**Angriff:** Zwei parallele `request-payout`-Calls mit type `bank` lesen denselben `balance_rappen` und schreiben beide einen reduzierten Stand / zwei Payout-Requests. Kein bedingtes Update / kein atomarer Deduct.

**Belege:** `server/api/affiliate/request-payout.post.ts`.

### H3 — Staff `/api/credit/use-for-appointment` missachtet Freeze

**Angriff:** Nach Auszahlungsantrag bucht Staff (Normalflow) Guthaben auf einen Termin. Endpoint selektiert nur `balance_rappen` und zieht ab — ohne `pending_withdrawal_rappen`. Student erhält Leistung + Banküberweisung auf dasselbe Guthaben.

**Belege:** `server/api/credit/use-for-appointment.post.ts`. Kontrast: `student-credits/use-for-appointment` respektiert Freeze.

### H4 — Parallele `/payments/process` → Credit Double-Spend über mehrere Payments

**Angriff:** Zwei pending Payments desselben Users; parallele Process-Calls. Per-Payment-Lock verhindert Doppelstart **derselben** Zahlung, aber beide lesen denselben Credit-Stand und deducieren non-atomar (kein `deduct_student_credit`). Saldo kann unter null / unter Freeze fallen.

**Belege:** `server/api/payments/process.post.ts` (Lock nur auf Payment-Row; Credit-Update ohne RPC).
