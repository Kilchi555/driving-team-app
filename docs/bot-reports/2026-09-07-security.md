## New findings

### 1. [Critical] Unauthenticated Stripe Connect Express account minting

- **Location:** `server/api/stripe/connect/create-account.post.ts`
- **Attacker:** Unauthenticated internet user
- **Controlled input:** `tenantId`, `email`, `businessName`
- **Attack path:** `POST /api/stripe/connect/create-account` with no auth. Handler initializes Stripe with `STRIPE_SECRET_KEY`, creates an Express connected account (`stripe.accounts.create`), then returns `accountId` and `onboardingUrl` from `accountLinks.create`.
- **Impact:** Abuse of platform Stripe credentials to mass-create Connect accounts, burn API quota/cost, and obtain onboarding links for attacker-controlled emails.
- **Evidence:** No `getAuthenticatedUser` / `requireAdminProfile` / internal secret; body fields drive account creation; response includes live onboarding URL.

### 2. [High] Unauthenticated Stripe Connect account status disclosure

- **Location:** `server/api/stripe/connect/account-status.get.ts`
- **Attacker:** Unauthenticated user who knows or obtains a Connect `accountId` (including from finding 1)
- **Controlled input:** `accountId` query parameter
- **Attack path:** `GET /api/stripe/connect/account-status?accountId=acct_...` with no auth. Handler retrieves the account via the platform secret and returns status fields.
- **Impact:** Disclosure of Connect KYC/requirements state and `business_profile` for arbitrary connected accounts.
- **Evidence:** No auth helper; `stripe.accounts.retrieve(accountId)`; response includes `requirements` and `business_profile`.

### 3. [High] Authenticated course test-reminder leaks cross-tenant registration PII

- **Location:** `server/api/admin/courses/send-test-course-reminder.post.ts`
- **Attacker:** Any authenticated low-privilege client
- **Controlled input:** `registrationId`, optional `overrideEmail`
- **Attack path:** Authenticate as client, `POST` with any confirmed `course_registration` UUID and attacker `overrideEmail`. Comment claims staff/admin only, but code only calls `getAuthenticatedUser` (no role/tenant gate). Service-role load of registration/course/session; email sent to override address with participant/course/session details.
- **Impact:** Cross-tenant student PII exfiltration (name/course/time/location) plus branded email abuse.
- **Evidence:** Auth check only; `course_registrations.select` by id without tenant filter; `recipientEmail = overrideEmail || reg.email`; `sendEmail`.

### 4. [High] Unauthenticated copy-default-categories pollutes any tenant catalog

- **Location:** `server/api/tenants/copy-default-categories.post.ts`
- **Attacker:** Unauthenticated internet user who knows a tenant UUID
- **Controlled input:** `tenant_id`
- **Attack path:** `POST /api/tenants/copy-default-categories` with victim `tenant_id`. No auth. Service role copies global template categories into that tenant.
- **Impact:** Cross-tenant booking catalog pollution / category configuration sabotage.
- **Evidence:** Handler starts with `readBody` + `getSupabaseAdmin` only; `categories.insert(... tenant_id)` after tenant lookup by body id.

### 5. [High] Authenticated ICS calendar connect enables SSRF

- **Location:** `server/api/staff/external-calendars.post.ts`
- **Attacker:** Any authenticated user (role unused; clients included)
- **Controlled input:** `action=connect`, `data.ics_url`
- **Attack path:** Authenticate as client, `POST` connect with attacker HTTPS ICS URL (redirects followed). Profile select is `id,tenant_id` only (no staff role gate). `probeIcsUrl` uses `fetch(url, { redirect: 'follow' })` with no private/link-local allowlist.
- **Impact:** Server-side request forgery against internal HTTPS targets (status/body probing via error paths) and calendar sync pollution for the caller's user id.
- **Evidence:** No role check; `inspectIcsUrlShape` only enforces initial `https`; `probeIcsUrl` has no SSRF host/IP blocking before fetch.
