### STILL-OPEN-B1 — Critical — Rebind completed Wallee tx → mark unpaid payment completed

- **Status:** Still open
- **Exact paths:**
  - `server/api/payments/update-wallee-id.post.ts` (L56–88)
  - `server/api/payments/status.post.ts` (L166–201) — customer `failed|cancelled|pending` → `syncAndResolvePayment`
  - `server/utils/wallee-payment-sync.ts` (L139–151, L236–260) — `mark_completed` with **no** amount/uniqueness/merchantReference check
  - Amplifiers: `pages/payment/failed.vue` calls status with `failed`; `server/api/cron/recover-pending-wallee-payments.get.ts` also completes from linked tx state without amount check
- **Attack story:**
  1. Customer owns unpaid payment **P** (e.g. CHF 90 lesson) with empty `wallee_transaction_id`.
  2. Completes any cheap real Wallee payment (e.g. CHF 5 top-up) → tx **T** is `FULFILL`.
  3. `POST /api/payments/update-wallee-id` `{ payment_id: P, wallee_transaction_id: T }` — allowed for owner when P has no id; no uniqueness, amount, or merchantReference binding.
  4. Hit `/payment/failed` or `POST /api/payments/status` with `status: 'failed'` → sync reads **T** fulfilled → sets **P** to `completed` **without** comparing captured CHF to P’s total.
  5. Same-amount variant: bind **T** to a second unpaid payment of matching CHF; forged/replayed webhook (unsigned; API+amount check pass) can complete every row sharing that `wallee_transaction_id`.
- **NEW vs still-open:** **Still open** — overwrite of existing different id is restricted for non-privileged, but empty-id attach + status sync upgrade remain.
- **Line evidence:**

### STILL-OPEN-B2 — High — Gift cards applied as discounts are not reserved at apply time

- **Status:** Still open (partial mitigation only)
- **Exact paths:**
  - Apply without consume: `server/utils/resolve-appointment-discount.ts` (L101–119), `server/api/appointments/apply-discount.post.ts` (L144–163, L302–308), `server/api/courses/enroll-wallee.post.ts` (L523–560), `server/api/payments/process-public.post.ts` (L239–280)
  - Deferred consume only: `server/api/wallee/webhook.post.ts` (L649–660), `server/utils/apply-student-credit.ts` (via `consumeGiftCardForPayment`)
  - `incrementAppointmentDiscountUsage` skips gift cards (only `discounts` / `voucher_codes`)
- **Attack story:**
  1. Obtain shop gift card (`vouchers`, `redeemed_at IS NULL`).
  2. Apply code to payment A (booking / apply-discount / course enroll) → server reduces `total_amount_rappen` / Wallee charge; **does not** set `redeemed_at`.
  3. Apply same code to payment B while A still unpaid — still passes `!redeemed_at`.
  4. Pay both at discounted amounts. First webhook consumes the card; second already charged less at the provider.
- **NEW vs still-open:** **Still open** — webhook consume closes sequential reuse after first successful Wallee completion, but not multi-checkout underpay before consume. Sync-only completion (`STILL-OPEN-B1`) also skips consume.
- **Line evidence:** apply-discount persists reduced total with no `redeemed_at` write (L302–308); webhook consume is post-completion (L649–660).

### STILL-OPEN-B3 — High — Course/shop charge paths ignore discount usage limits

- **Status:** Still open
- **Exact paths:**
  - `server/api/courses/enroll-wallee.post.ts` (L507–560) — validates type/expiry/amount only; **no** `usage_limit` / `max_redemptions` / `max_per_user`
  - `server/api/payments/process-public.post.ts` (L220–280) — same
  - `server/api/shop/create-payment.post.ts` (L193–241) — recomputes discount from DB IDs but does not select/enforce `usage_limit` or increment
  - Webhook increments after pay (`wallee/webhook.post.ts` L1165–1199) but charge already happened
- **Attack story:** Tenant issues promo with `usage_limit=1` or `max_redemptions=1`. Attacker enrolls / shops repeatedly with that code. Server applies full discount to each Wallee charge. Counters may increment after pay, but next enrollment still applies the code because charge paths never enforce the limit.
- **NEW vs still-open:** **Still open** — appointment resolve path checks limits (`resolve-appointment-discount.ts` L80, L137); course/shop do not.
- **Line evidence:** enroll-wallee discount block ends at amount math with no limit check (L547–560); shop discount select omits `usage_limit` (L204–208).

## Suggested fixes (report only)

**Part A:** Atomic freeze/spend (`available = balance - pending`); CAS debits; redeem-before-credit; affiliate freeze parity.

**Part B:**
1. Stop client-set `wallee_transaction_id`; bind only from server create-transaction; uniqueness + merchantReference + amount checks.
2. `syncAndResolvePayment` / recover cron: require captured ≥ expected before `mark_completed`; refuse if tx already linked to another payment.
3. Reserve/consume gift cards at apply (`redeemed_at IS NULL` CAS) before reducing charge amount.
4. Enforce `usage_limit` / `max_redemptions` / `max_per_user` on enroll-wallee, process-public, shop/create-payment before creating the charge.
5. Tighten `payments` UPDATE RLS: clients must not set `payment_status` to paid states (or remove client UPDATE; route through verified APIs only).
