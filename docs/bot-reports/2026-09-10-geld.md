## Findings

### 1. Critical — Wallee tx rebind → high-amount payment marked completed without amount/uniqueness check

**Previously known:** Yes (C1) — **RECONFIRMED**

**Files + lines:**
- `server/api/payments/update-wallee-id.post.ts` — L56–88 (owner may set `wallee_transaction_id` when unset; no verify of amount, merchantReference, ownership, or prior binding)
- `server/api/payments/process.post.ts` — L465–501 (existing tx in FULFILL/COMPLETED/SUCCESSFUL → `payment_status: completed` with no amount compare)
- `server/utils/wallee-payment-sync.ts` — `applyWalleeSyncDecision` L139–151; `syncAndResolvePayment` L236–260 (state-only → `mark_completed`)
- Callers of sync: `server/api/payments/status.post.ts` L178–201; `server/api/payments/release-processing-lock.post.ts` L69–89
- Same completion gap: `server/api/wallee/create-transaction.post.ts` L114–121
- Contrast (webhook OK): `server/api/wallee/webhook.post.ts` L542–578 (captured vs `total_amount_rappen`)
- DB: `sql_migrations/20260620_wallee_space_id_multitenancy.sql` — unique is only on `payment_wallee_transactions`, **not** on `payments` (payments index L18–20 is non-unique)

**Attack story (step by step):**
1. Attacker completes (or observes) a **low-amount** Wallee payment in the same tenant space (e.g. CHF 5) → learns `wallee_transaction_id` `T` (own receipt/URL is enough; same-tenant peer ID also works if known).
2. Attacker has a **high-amount** pending payment `P` (e.g. CHF 500) with `wallee_transaction_id` still null (normal new lesson payment).
3. Attacker calls `POST /api/payments/update-wallee-id` with `{ payment_id: P, wallee_transaction_id: T }`. Overwrite of a *different* existing id is blocked for non-staff, but **first attach is allowed** with no Wallee/amount/uniqueness check. Update does not set `wallee_space_id`.
4. Attacker calls `POST /api/payments/process` with `paymentId: P`. Code reads `T` at Wallee, sees completed state, updates `P` to `completed` / `paid_at` **without** comparing captured CHF to `P.total_amount_rappen`.
5. Alternate completion paths after step 3: put `P` into `processing` then `status`/`release-processing-lock` sync → `mark_completed`; or `create-transaction` with `orderId: P` → marks completed on completed state (L114–121).
6. Lesson/appointment is treated as paid; school never received the high amount for `P`. Webhook underpay check does **not** protect these client-driven sync/process paths.

**Why confirmed:** Current code still allows client first-time bind of any tx id; process/sync/create-transaction complete on Wallee **state only**; webhook amount check is not reused; `payments` has no uniqueness on `(space, tx)`.

### 2. Critical — Frozen withdrawal spendable via `/api/payments/process`

**Previously known:** Yes (C2) — **RECONFIRMED**

**Files + lines:**
- `server/api/payments/process.post.ts` — L123–137 (`select('balance_rappen')` only); L217–221 / L304–313 / L419–428 (RMW deduct from full `balance_rappen`)
- Contrast: `server/utils/wallet-atomic.ts` `deductStudentCredit` + `migrations/20260826_wallet_atomic_ops.sql` L19–26 (available = balance − pending) — **unused** by process
- Freeze writer: `server/api/customer/request-credit-withdrawal.post.ts` L108–116 (`pending_withdrawal_rappen` += amount; balance unchanged)
- Admin later: `server/api/admin/complete-withdrawal.post.ts` L64–78 (deducts pending from balance again)

**Attack story:**
1. Student has `balance_rappen = 10000` (CHF 100), requests IBAN withdrawal of CHF 100 → `pending_withdrawal_rappen = 10000`, balance still 10000.
2. Student calls `/api/payments/process` on a pending lesson. Available credit computed as **10000** (ignores pending).
3. Payment completes (full or partial) with credit; balance reduced; frozen flag still set.
4. Admin runs complete-withdrawal → deducts pending from (already spent) balance / pays bank. Same funds used for lesson **and** payout.

**Why confirmed:** process never reads `pending_withdrawal_rappen` and never calls `deduct_student_credit`.

### 3. Critical — Affiliate `request-payout` ignores `pending_withdrawal_rappen`

**Previously known:** Yes (C3) — **RECONFIRMED**

**Files + lines:**
- `server/api/affiliate/request-payout.post.ts` — L58–73 (balance check on `balance_rappen` only); L90–96 (RMW deduct full balance)

**Attack story:**
1. User freezes wallet via customer withdrawal (`pending_withdrawal_rappen > 0`, balance still high).
2. Same user (affiliate) calls `request-payout` type `bank` for up to full `balance_rappen`.
3. Check passes; balance deducted for payout hold while frozen slice was never excluded → overlapping claims on the same rappen vs pending IBAN withdrawal / complete-withdrawal.

**Why confirmed:** select/check/update ignore pending; no available-wallet helper.

### 4. High — Concurrent `request-credit-withdrawal` race (RMW; unused `add_pending_withdrawal`)

**Previously known:** Yes (H1) — **RECONFIRMED**

**Files + lines:**
- `server/api/customer/request-credit-withdrawal.post.ts` — L47–64 (read available); L108–116 (write `pending = stalePending + amount` without conditional/RPC)
- Unused atomic path: `server/utils/wallet-atomic.ts` L64–80; `migrations/20260826_wallet_atomic_ops.sql` L78–105 (`add_pending_withdrawal` enforces available under row update)

**Attack story:**
1. Balance CHF 100, pending 0. Attacker fires two parallel withdrawal requests for CHF 100 (or two for CHF 80).
2. Both reads see `available = 100` and pass the check.
3. Both inserts create `withdrawal_pending` txs; both writes set pending from the same stale base → last-write-wins under-freeze **or** two pending txs totaling more than safely frozen.
4. Wallet accounting no longer matches payout obligations; combined with C2 spend paths, funds can be double-claimed.

**Why confirmed:** classic read-modify-write; RPC exists but is never called from this endpoint (only tests/wrapper).

### 5. High — Affiliate bank payout concurrent race

**Previously known:** Yes (H2) — **RECONFIRMED**

**Files + lines:**
- `server/api/affiliate/request-payout.post.ts` — L58–66 read; L90–96 update `balance_rappen: currentBalance - amount` without `WHERE balance >= amount` / RPC

**Attack story:**
1. Balance CHF 100. Two parallel `request-payout` bank requests for CHF 100.
2. Both see balance 100; both deduct to 0; both create payout requests / txs.
3. Result: two payout obligations from one balance (or lost-update inconsistency).

**Why confirmed:** non-atomic RMW; no row-level balance guard.

### 6. High — `/api/credit/use-for-appointment` spends frozen balance

**Previously known:** Yes (H3) — **RECONFIRMED**

**Files + lines:**
- `server/api/credit/use-for-appointment.post.ts` — L105–110 (`balance_rappen` only); L151–169 (deduct up to full balance)
- Contrast OK: `server/api/student-credits/use-for-appointment.post.ts` L92–107 (subtracts `pending_withdrawal_rappen`)

**Attack story:**
1. Student has pending withdrawal freeze.
2. Staff/admin uses `/api/credit/use-for-appointment` (staff-only) against that student’s appointment for up to full raw balance.
3. Frozen slice is spent on the lesson while `pending_withdrawal_rappen` remains; later complete-withdrawal still pays out freeze.

**Why confirmed:** staff endpoint still ignores freeze; sibling student-credits endpoint already respects it.

### 7. High — Concurrent `/payments/process` credit double-spend

**Previously known:** Yes (H4) — **RECONFIRMED**

**Files + lines:**
- `server/api/payments/process.post.ts` — L123–137 parallel balance read; L181–208 lock is **per payment** only; L304–313 / L419–428 absolute `balance_rappen` write
- Unused: `deduct_student_credit` RPC (atomic available check)

**Attack story:**
1. Student has CHF 100 credit and two distinct pending payments (or two tabs on different paymentIds).
2. Two concurrent `/api/payments/process` calls each claim their own payment lock successfully.
3. Both read `balance_rappen = 10000`; both apply credit and write a new absolute balance.
4. More credit applied across payments than existed (lost update / double spend).

**Why confirmed:** payment-level lock does not serialize wallet updates; no `deduct_student_credit`.
