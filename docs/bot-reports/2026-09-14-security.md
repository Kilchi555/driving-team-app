## New findings

### 1. [Critical] Authenticated client can start Stripe checkout that deactivates staff and changes tenant plan

- **Location:** `server/api/stripe/create-checkout-session.post.ts`
- **Attacker:** Authenticated low-privilege client in a tenant without an active Stripe subscription
- **Controlled input:** `plan`, `addons`, `withWallee` (default true), `staffToDeactivate[]`
- **Attack path:** Client `POST`s `/api/stripe/create-checkout-session` with `staffToDeactivate` set to victim staff UUIDs. Auth is `getAuthenticatedUser` + tenant only (no admin role). Default `withWallee` creates a 30-day trial Checkout; completing it (no immediate charge during trial) fires Stripe webhooks. `handleSubscriptionUpsert` reads `metadata.staff_to_deactivate` and sets `users.is_active=false` (scoped to the caller tenant) and writes `subscription_plan`/addons onto the tenant.
- **Impact:** Same-tenant staff lockout and unauthorized tenant plan/feature changes without admin privileges.
- **Evidence:** No admin gate (unlike `update-subscription.post.ts`); `staffToDeactivate` copied into `subscription_data.metadata`; webhook deactivates those user IDs on subscription upsert.

### 2. [High] Authenticated sync-subscription applies arbitrary completed Checkout sessions to caller tenant

- **Location:** `server/api/stripe/sync-subscription.post.ts`
- **Attacker:** Any authenticated tenant user who obtains a completed Stripe Checkout `session_id`
- **Controlled input:** `sessionId`
- **Attack path:** Attacker authenticates as Tenant A, supplies another tenant’s completed `session_id` (e.g. from success URL `?session_id=`), and `POST`s `/api/stripe/sync-subscription`. Handler loads the session/subscription with `STRIPE_SECRET_KEY` and updates the caller tenant without comparing `subscription.metadata.tenant_id` or Stripe customer to the caller.
- **Impact:** Cross-tenant subscription hijack: steal paid entitlements or corrupt Stripe customer/subscription bindings.
- **Evidence:** No admin role gate; no `metadata.tenant_id`/customer binding check before `tenants.update`.

### 3. [High] Unauthenticated pendencies update-overdue mass-mutates tasks across all tenants

- **Location:** `server/api/admin/pendencies/update-overdue.post.ts`
- **Attacker:** Unauthenticated internet user
- **Controlled input:** None (POST trigger)
- **Attack path:** Attacker `POST`s `/api/admin/pendencies/update-overdue` with no auth. Service role updates every overdue pendency in (`pendent`, `in_bearbeitung`) to `überfällig` with no tenant or cron-secret gate.
- **Impact:** Platform-wide operational task integrity sabotage across tenants.
- **Evidence:** No `getAuthenticatedUser`/`CRON_SECRET`; service-role update filtered only by `due_date`/`status`.

### 4. [High] Tenant admin can trigger whitelabel builds and overwrite app_configs for arbitrary tenants (tip only)

- **Location:** `server/api/whitelabel/create-app.post.ts`
- **Attacker:** Authenticated tenant admin (`role=admin`) in any tenant
- **Controlled input:** `tenantId`
- **Attack path:** On tip, admin `POST`s `/api/whitelabel/create-app` with a victim `tenantId`. Gate checks `role===admin` only, not tenant ownership. Handler upserts `app_configs` for the victim and, when `SIMY_GITHUB_PAT` is set, dispatches `build-whitelabel.yml`.
- **Impact:** Cross-tenant mobile-app config overwrite and abuse of platform GitHub Actions credentials.
- **Evidence (tip):** No `authUser.tenant_id` match to body `tenantId`; upsert + `workflow_dispatch` use caller-supplied `tenantId`. Current `main` uses `requireSuperAdmin` (not exploitable there).

### 5. [Medium] Unauthenticated get-student-instructors discloses student–staff relationships (tip only)

- **Location:** `server/api/admin/get-student-instructors.post.ts`
- **Attacker:** Unauthenticated internet user who knows student UUIDs
- **Controlled input:** `studentIds` array
- **Attack path:** On tip, attacker `POST`s `/api/admin/get-student-instructors` with `studentIds`. No auth. Service role returns appointment `user_id`/`staff_id` mappings and instructor first/last names with no tenant scope.
- **Impact:** Cross-tenant disclosure of student–instructor relationships and instructor PII.
- **Evidence (tip):** No auth helper; `createClient(SERVICE_ROLE)`; appointments/users selects by caller-supplied `studentIds`. Current `main` uses `requireAdminProfile` + tenant checks (not exploitable there).
