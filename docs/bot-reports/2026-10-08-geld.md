## 3–4. Findings (re-check)

### 1. Critical — Wallee tx rebind → high-amount payment marked completed without amount/uniqueness check

**Status: CONFIRMED**

**Attack story:** Attacker (or same-tenant peer) obtains a low-amount completed Wallee `transactionId` `T`. They own a high-amount pending payment `P` with null `wallee_transaction_id`. `POST /api/payments/update-wallee-id` allows first-attach of any `T` with no Wallee read, amount check, merchantReference bind, or uniqueness. Then `POST /api/payments/process`, `create-transaction`, or client sync via `status` / `release-processing-lock` → `wallee-payment-sync` marks `P` completed on Wallee **state only** (FULFILL/COMPLETED/SUCCESSFUL). Webhook underpay (`shouldRejectWalleeCaptureMismatch`) is not used on these paths. `payments` still has no unique constraint on `(wallee_space_id, wallee_transaction_id)` (only `payment_wallee_transactions` is unique). Identity-block (`#308`) holds mismatched payer identity; it does not amount-gate this rebind.

**Evidence:**
- `server/api/payments/update-wallee-id.post.ts:56–88` — overwrite of a *different* id blocked for non-staff; first-attach still writes arbitrary `wallee_transaction_id` with no amount/API verify.
- `server/api/payments/process.post.ts:576–611` — existing completed tx → `completeCapturedWalleePayment` (non-course) with no capture vs remaining compare; course path checks via fulfill helpers.
- `server/utils/wallee-payment-sync.ts:175–206` — `applyWalleeSyncDecision` `mark_completed` is state→DB only.
- `server/api/wallee/create-transaction.post.ts:132–173` — non-course completed reuse updates `payment_status: 'completed'` without amount gate.
- `server/api/cron/recover-pending-wallee-payments.get.ts:44–59` vs `:62–86` — amount mismatch enforced for **course** atomic fulfill only; generic `recoverToCapturedStatus` → `completeCapturedWalleePayment` does not.
- Contrast OK: `server/api/wallee/webhook.post.ts` + `server/utils/wallee-remaining-amount.ts` (`shouldRejectWalleeCaptureMismatch`).

### 2. Critical — Frozen withdrawal spendable via `/api/payments/process`

**Status: CONFIRMED**

**Attack story:** Student freezes CHF 100 via `request-credit-withdrawal` (`pending_withdrawal_rappen` rises; `balance_rappen` unchanged). They then pay a lesson through `/api/payments/process`. Process selects only `balance_rappen`, treats full balance as available, and RMW-updates balance (full or partial credit). Later admin `complete-withdrawal` still pays out / clears pending against the same wallet → double use of frozen funds.

**Evidence:**
- `server/api/payments/process.post.ts:173–187` — `select('balance_rappen')` only; `availableCredit = creditData?.balance_rappen`.
- `server/api/payments/process.post.ts:403–412` and `:518–527` — deduct via plain `.update({ balance_rappen: newBalance })`.
- Atomic helper unused here: `server/utils/wallet-atomic.ts` `deductStudentCredit` / `migrations/20260826_wallet_atomic_ops.sql` (`balance - pending >= amount`).

### 3. Critical — Affiliate `request-payout` ignores `pending_withdrawal_rappen`

**Status: CONFIRMED**

**Attack story:** Same freeze as above. Affiliate with `type: 'bank'` requests payout up to full `balance_rappen`. Check and deduct ignore pending → payout hold overlaps frozen IBAN withdrawal.

**Evidence:**
- `server/api/affiliate/request-payout.post.ts:59–73` — `select('balance_rappen')`; `currentBalance < amount_rappen`.
- `server/api/affiliate/request-payout.post.ts:91–96` — `update({ balance_rappen: newBalance })` with no pending subtraction and no row-level available guard.

### 4. High — Concurrent `request-credit-withdrawal` RMW (unused `add_pending_withdrawal`)

**Status: CONFIRMED**

**Attack story:** Two parallel requests each read available = balance − pending, both pass, both insert withdrawal rows and write `pending = stalePending + amount`. Without conditional update / RPC, frozen total can exceed spendable balance.

**Evidence:**
- `server/api/customer/request-credit-withdrawal.post.ts:49–58, 108–116` — read-modify-write on `pending_withdrawal_rappen`.
- Unused: `addPendingWithdrawal` in `server/utils/wallet-atomic.ts` + `add_pending_withdrawal` in `migrations/20260826_wallet_atomic_ops.sql`.

---

### 5. High — Affiliate bank payout concurrent race

**Status: CONFIRMED**

**Attack story:** Two parallel `request-payout` bank calls both read the same `balance_rappen`, both pass the sufficiency check, both write `balance - amount`. Wallet can go negative or double-hold the same funds into two `affiliate_payout_requests`.

**Evidence:**
- `server/api/affiliate/request-payout.post.ts:59–96` — non-atomic read then unconditional update; no `deduct_student_credit` / compare-and-swap.

---

### 6. High — `/api/credit/use-for-appointment` spends frozen balance

**Status: FIXED** (unchanged since 2026-09-17)

**Attack story (closed):** Previously staff could apply full `balance_rappen` including frozen pending. Current endpoint delegates to `applyCreditToPayment` → RPC `apply_credit_to_payment`, which computes available as `balance - pending` and debits with `balance - pending >= v_use` under `FOR UPDATE`.

**Evidence:**
- `server/api/credit/use-for-appointment.post.ts:10,127` — calls `applyCreditToPayment(...)`.
- `server/utils/apply-credit-to-payment.ts` — RPC wrapper.
- `migrations/20260915_apply_credit_to_payment.sql` — freeze-aware atomic debit.

---

### 7. High — Concurrent `/payments/process` credit double-spend across payments

**Status: CONFIRMED**

**Attack story:** Per-payment lock (`pending` → `processing`) stops double process of one payment, but two concurrent processes on **different** pending payments both read the same `balance_rappen`, both deduct up to that balance via plain updates → overspend beyond available wallet (and beyond freeze if finding 2 also applies).

**Evidence:**
- `server/api/payments/process.post.ts` — payment claim lock is per `payment.id` (`:231–258`); credit path (`:403–412`, `:518–527`) is still non-atomic balance RMW, not `deduct_student_credit`.
