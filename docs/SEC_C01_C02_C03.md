**When to use:** Investigating client `UPDATE` on `users.role` / `tenant_id`; 401 on marketing overview; resend-confirmation leaking tokens; applying or verifying the privilege-freeze migration.

## Intent

Three P0 holes closed together:

| ID | Problem | Fix |
|----|---------|-----|
| **SEC-C01** | Authenticated clients could escalate `users.role` / change `tenant_id` / `admin_level` under `user_update_own` | BEFORE UPDATE trigger + column REVOKE |

## SEC-C01 — `prevent_users_privilege_escalation`

Migration: `migrations/20260903_sec_c01_users_privilege_freeze.sql`.

| Actor | May change `role` / `tenant_id` / `admin_level`? |
|-------|--------------------------------------------------|
| `service_role` JWT (Data API) | Yes |
| SQL session with **no** JWT context (console / migrations) | Yes |
| `authenticated` / `anon` Data API | **No** — exception `42501` |

Trigger is `SECURITY DEFINER` but **must not** trust `current_user` (always the function owner). It inspects `auth.role()` / JWT claim role / claims JSON.

Defense in depth: `REVOKE UPDATE (role, tenant_id, admin_level)` from `PUBLIC`, `anon`, `authenticated`. Under some Supabase grant layouts the REVOKE alone may be weak — **the trigger is the enforceable control**.

Privileged mutations for real admin flows continue through **service-role** server APIs (there is no authenticated staff UPDATE policy on `public.users` for these columns).

## SEC-C02 — marketing overview

| Item | Contract |
|------|----------|
| Route | `GET /api/tenant-admin/marketing-overview` |
| Gate | `requireSuperAdmin(event)` before any aggregation |
| Denial | Preserve 401/403 from the helper; remap only unexpected failures |

Sibling tenant-admin routes that already required auth are the pattern to follow for any new platform marketing endpoints.

---

## SEC-C03 — resend confirmation

| Layer | Rule |
|-------|------|
| Auth | `requireAdminProfile` (admin / staff / super_admin) |
| Tenant | Non–`super_admin` must match `appointment.tenant_id` |
| Token | May create/store `confirmation_token` server-side; **never** select it into the JSON response |
| Send | `dispatchAppointmentConfirmation` (clears prior sent markers so a true resend can fire) |
| Response | `success`, `skipped`, `reason`, `emailSent`, `emailQueued`, `message` only |
| Logs | Appointment id / tenant / send flags — **no** token or confirmation link |

---

## Pitfalls

- Client-side profile editors must not assume they can PATCH `role` / `tenant_id` — expect DB exception after the migration.
- Do not “fix” C01 by weakening the trigger to trust `current_user`.
- Marketing overview without super-admin is a cross-tenant data leak — keep the gate first line of the handler.
- Returning `confirmationToken` “for the UI to build a link” reopens C03; links belong in the email only.
